1. Зачем веб-приложению безопасность

Веб-приложение получает запросы из недоверенной среды: браузера пользователя, мобильного клиента, curl, Postman или программы злоумышленника. Нельзя считать, что кнопка, скрытая в интерфейсе, защищает сервер: запрос к POST /units можно отправить вручную. Защита должна жить на сервере.

Три базовые цели

ЦельПростой вопросПример в проекте
КонфиденциальностьКто не должен увидеть данные?Пароль не возвращается из API; refresh в БД хранится только как hash.
ЦелостностьКто не должен изменить данные?Пользователь с UNITS_READ не может создать единицу.
ДоступностьКто не должен «уронить» сервис?Ограничения запросов, защита от перебора паролей, разумные таймауты.

Role и authority: почему не одно и то же

Роль — удобное бизнесовое имя: «Кладовщик», «Администратор». Authority — атомарное действие: UNITS_READ. Можно дать двум разным ролям одно authority. В Spring выражение hasRole("ADMIN") обычно ищет authority ROLE_ADMIN; выражение hasAuthority("UNITS_READ") ищет строку буквально. Наш проект строится на конкретных permissions, поэтому hasAnyAuthority здесь правильнее, чем искусственно заменить всё на ADMIN.

3. Как работает Spring Security «из коробки»

Что такое HTTP, servlet и filter

Браузер отправляет HTTP-запрос: метод, URL, заголовки, тело. В Spring Boot встроенный веб-сервер (обычно Tomcat) принимает его. Servlet — Java-объект, который умеет обработать HTTP-запрос. Spring MVC использует центральный servlet DispatcherServlet: он находит нужный метод контроллера.

Filter — объект, который запускается до servlet и может либо пропустить запрос дальше, либо остановить/изменить его. Это удобно для безопасности: аутентификация должна произойти до вызова контроллера.

Браузер / Postman | v Встроенный Tomcat | v SecurityFilterChain: [Filter 1] -> [Filter 2] -> ... -> [JWT filter] | | | кладёт Authentication в SecurityContext v DispatcherServlet -> Controller -> Service -> Repository -> PostgreSQL | v HTTP response

Что добавляет starter-security без настройки

Подключение spring-boot-starter-security добавляет фильтры безопасности. Если не написать собственную конфигурацию, Spring Boot обычно:

  • закрывает почти все URL;
  • создаёт временного пользователя и печатает пароль в лог;
  • включает form login / Basic в зависимости от запроса;
  • создаёт сессию после входа.

Это полезно как безопасный старт, но почти никогда не является готовой конфигурацией API. Мы заменяем поведение собственным SecurityFilterChain.

Два разных момента: login и обычный запрос

LOGIN (один раз) API REQUEST (много раз) ----------------- ------------------------ логин + пароль Authorization: Bearer <access> | | AuthenticationManager JWT filter | | UserDetailsService + PasswordEncoder JWTService: подпись + exp | | успех -> access/refresh UserDetailsService: права из БД | SecurityContext -> Controller

4. Виды аутентификации и 2FA

Факторы — это разные доказательства личности. Надёжная схема не обязана собирать все факторы; она выбирает их по риску и удобству.

ФакторЧто доказывает пользовательПримерыСлабые места
Knowledge-based («знаю»)Секрет, который должен знать только он.Пароль, PIN, контрольный вопрос.Фишинг, повторное использование, утечки, подбор.
Possession-based («владею»)Есть физический или цифровой предмет.Телефон, аппаратный ключ FIDO2, карточка, приложение-аутентификатор.Кража/потеря устройства, SIM-swap.
Inherence («являюсь»)Биометрический признак.Отпечаток, Face ID.Ошибки распознавания; биометрию нельзя «сменить» как пароль.

Однофакторная и двухфакторная аутентификация

2FA — минимум два разных фактора. Пароль и второй пароль — не 2FA: оба «что знаю». Пароль + код из приложения — 2FA: «знаю» + «владею телефоном».

SMS-код

Сервер после пароля создаёт одноразовый код с коротким TTL, отправляет SMS и ждёт подтверждение. Плюс — пользователь уже умеет пользоваться SMS. Минусы — стоимость, доставка, перехват/переоформление SIM, фишинг. Для высокой безопасности SMS хуже TOTP/FIDO2, но лучше одного пароля.

Google Authenticator и TOTP

Google Authenticator — один из клиентов протокола TOTP (Time-based One-Time Password). При включении 2FA сервер генерирует секрет и показывает QR-код. Приложение и сервер знают один секрет и одинаковое текущее время; оба считают короткий код, обычно меняющийся раз в 30 секунд. Сервер хранит секрет защищённо, не пароль от Google Authenticator.

Важно: Google Authenticator не «проверяет пользователя через Google». Это локальный генератор TOTP-кодов. Сервер сам проверяет код по общему секрету.

5. Базовая настройка Spring Security с нуля

Минимальная модель данных

User ---- many-to-many ---- Role ---- many-to-many ---- Permission | | | username, passwordHash name code = UNITS_READ enabled USERS_WRITE

Пароль никогда не хранится как обычный текст. В базе — только медленный salted hash BCrypt. При логине Spring вызывает passwordEncoder.matches(rawPassword, passwordHash).

Порядок создания

  1. Добавить spring-boot-starter-security.
  2. Подготовить пользователя и permissions в БД.
  3. Написать AppPrincipal implements UserDetails.
  4. Написать UserDetailsService, который находит principal по username.
  5. Объявить PasswordEncoder (BCrypt) и AuthenticationManager.
  6. Написать SecurityFilterChain: публичные URL, защита остальных, session policy.
  7. Поставить @PreAuthorize на действия, а не только скрыть кнопку на UI.

Фрагмент нашего SecurityConfiguration

@Configuration
@EnableWebSecurity
@EnableMethodSecurity
public class SecurityConfiguration {

    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder(12);
    }

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity httpSecurity,
                                           JWTAuthenticationFilter jwtAuthenticationFilter) throws Exception {
        return httpSecurity
            .csrf(AbstractHttpConfigurer::disable)
            .httpBasic(AbstractHttpConfigurer::disable)
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(a -> a
                .requestMatchers("/login/**", "/css/**", "/js/**", "/").permitAll()
                .anyRequest().authenticated())
            .addFilterBefore(jwtAuthenticationFilter, UsernamePasswordAuthenticationFilter.class)
            .build();
    }

    @Bean
    public AuthenticationManager authenticationManager(
            AuthenticationConfiguration authenticationConfiguration) throws Exception {
        return authenticationConfiguration.getAuthenticationManager();
    }
}
Строка / типЗачем
@ConfigurationГоворит Spring: этот класс создаёт бины конфигурации.
@EnableWebSecurityВключает web security инфраструктуру.
@EnableMethodSecurityВключает @PreAuthorize на методах.
@Bean PasswordEncoderОдин общий объект для hash и проверки пароля.
BCryptPasswordEncoder(12)12 — work factor: безопасность выше, проверка медленнее. Это намеренно.
@Bean AuthenticationManagerЭкспортирует менеджер наружу в Spring Context. Без этого бина контроллер не сможет его заинжектить (будет NoSuchBeanDefinitionException).
AuthenticationConfigurationАвтоматически связывает наши бины UserDetailsService и PasswordEncoder в DaoAuthenticationProvider и отдаёт готовый AuthenticationManager.
STATELESSНе создавать/не читать HTTP session; каждый запрос несёт собственное доказательство.
requestMatchers(...).permitAll()Публичные пути, которые можно вызвать до входа.
anyRequest().authenticated()Без Authentication в SecurityContext дальше не пройти.
addFilterBeforeНаш JWT-фильтр запускается до стандартного username/password фильтра.
Цепочка проверки подлинности (Запомнить наизусть):
AuthenticationManager (ProviderManager) ➔ DaoAuthenticationProvider ➔ UserDetailsService.loadUserByUsername() ➔ PasswordEncoder.matches(raw, hash) ➔ Возврат подтверждённого Authentication (Principal=AppPrincipal, Authorities=права, Credentials=null).
Как искать в документации (docs.spring.io):
• Логин, пароли, токены, провайдеры — ищи в /servlet/authentication/... («Кто ты?»).
• Роли, права, @PreAuthorize, доступ к URL — ищи в /servlet/authorization/... («Что тебе можно?»).
• В IntelliJ IDEA: Ctrl + Q над классом или кнопка Download Sources, чтобы читать комментарии авторов вместо декомпилированного байткода.

6. HTTP Basic

Теория

HTTP Basic передаёт в каждом запросе заголовок Authorization: Basic Base64(username:password). Base64 — кодировка, не шифрование: строку легко декодировать. Basic допустим только через HTTPS и подходит для простых API, service-to-service или учебного старта. Для SPA хранить пароль и прикладывать его к каждому запросу — плохая долгосрочная схема.

Схема Basic

Browser: Authorization: Basic base64("admin:password") | v Spring BasicAuthenticationFilter | v AuthenticationManager | | v v UserDetailsService PasswordEncoder.matches | | +----------- успех --------+ | v SecurityContext -> @PreAuthorize -> Controller

Как внедрить с нуля

  1. Подключить Security starter.
  2. Создать UserDetails и UserDetailsService.
  3. Создать BCrypt PasswordEncoder.
  4. В SecurityFilterChain включить httpBasic(Customizer.withDefaults()).
  5. Для первого опыта отключить form login; выбрать session policy осознанно.
  6. Поставить method security.
  7. Проверить curl/Postman с Basic header.

Ключевые объекты нашего проекта

public class AppPrincipal implements UserDetails {
    private final User user;

    @Override
    public Collection<? extends GrantedAuthority> getAuthorities() {
        return user.getRoles().stream()
            .flatMap(role -> role.getPermissions().stream())
            .map(Permission::authority)
            .collect(Collectors.toSet());
    }

    @Override
    public String getPassword() { return user.getPasswordHash(); }

    @Override
    public String getUsername() { return user.getUsername(); }
}
ФрагментПояснение
implements UserDetailsАдаптер между собственной сущностью User и контрактом Spring Security.
Collection<? extends GrantedAuthority>Список разрешений. ? extends разрешает любой конкретный тип, реализующий интерфейс.
flatMapУ пользователя много ролей, у каждой много permissions. flatMap превращает «список списков» в один поток permissions.
map(Permission::authority)Ссылка на метод: каждый Permission превращается в Spring-совместимый GrantedAuthority.
getPassword()Возвращает hash из БД, не сырой пароль. Spring использует его только для matches.
@Service
@RequiredArgsConstructor
public class UserDetailsServiceImpl implements UserDetailsService {
    private final UserRepository userRepository;

    @Override
    public UserDetails loadUserByUsername(String username) {
        User user = userRepository.findByUsername(username)
            .orElseThrow(() -> new UsernameNotFoundException("..."));
        return new AppPrincipal(user);
    }
}

UserDetailsService отвечает только на вопрос «найди пользователя по логину и отдай Security-представление». Он не сравнивает пароль вручную: это задача AuthenticationManager и PasswordEncoder.

7. JWT (JSON Web Token)

Теория

JWT — компактный подписанный билет. Он обычно выглядит как три Base64URL-части: header.payload.signature. Это не зашифрованный контейнер: payload можно прочитать. Подпись доказывает, что header/payload выданы сервером и не изменены.

header: { "alg": "HS256", "typ": "JWT" } payload: { "sub": "admin", "iat": ..., "exp": ... } signature: HMAC-SHA256(base64url(header) + "." + base64url(payload), serverSecret)

У нас симметричная подпись HMAC: один secret и создаёт, и проверяет подпись. Он живёт на сервере в app.jwt.secret. При проверке JJWT пересчитывает подпись тем же ключом и проверяет exp. Клиент ключ никогда не получает.

Схема JWT в нашем проекте

POST /login/auth { username, password } -> AuthenticationManager -> UserDetailsService + BCrypt -> JWTService.generateToken(username) -> { accessToken: "eyJ..." } GET /units/ Authorization: Bearer eyJ... -> JWTAuthenticationFilter -> JWTService.isTokenValid + extractUsername -> UserDetailsService.loadUserByUsername -> SecurityContextHolder.setAuthentication(...) -> UnitController + @PreAuthorize

Алгоритм внедрения JWT

  1. Добавить три JJWT зависимости одной версии: api, impl, jackson.
  2. Положить secret и срок access в конфиг (в проде — env/secret storage, не Git).
  3. Создать JWTService: generate, parse, extract username, validate.
  4. Создать filter, читающий Authorization: Bearer.
  5. При валидном токене построить Authentication и положить в SecurityContext.
  6. Создать контроллер логина через AuthenticationManager.
  7. Отключить Basic, перейти на STATELESS, зарегистрировать фильтр.
  8. Из фронта хранить access и прикладывать только к защищённым API.

JWTService: разбор текущего кода

public String generateToken(String username) {
    Instant now = Instant.now();
    return Jwts.builder()
        .subject(username)
        .issuedAt(Date.from(now))
        .expiration(Date.from(now.plus(tokenExpiration)))
        .signWith(signingKey())
        .compact();
}
СтрокаСмысл
Instant nowТекущий момент по UTC; удобен для времени безопасности.
Jwts.builder()Builder JJWT: собирает claims и подпись пошагово.
subject(username)Стандартный claim sub — идентификатор пользователя.
issuedAtiat, время создания билета.
expirationexp; после него билет недействителен.
signWithСтавит криптографическую подпись ключом сервера.
compact()Финально сериализует JWT в строку.

JWT filter: суть

String header = request.getHeader("Authorization");
if (header == null || !header.startsWith("Bearer ")) {
    filterChain.doFilter(request, response);
    return;
}
String token = header.substring("Bearer ".length()).trim();
if (SecurityContextHolder.getContext().getAuthentication() == null
        && jwtService.isTokenValid(token)) {
    String username = jwtService.extractUsername(token);
    UserDetails user = userDetailsService.loadUserByUsername(username);
    var auth = new UsernamePasswordAuthenticationToken(
        user, null, user.getAuthorities());
    SecurityContextHolder.getContext().setAuthentication(auth);
}
filterChain.doFilter(request, response);

Нет Bearer — фильтр не является ошибкой сам по себе: публичный endpoint может работать. Но защищённый endpoint позднее увидит пустой SecurityContext и ответит 401. Три аргумента в UsernamePasswordAuthenticationToken означают «пользователь уже аутентифицирован»; второй аргумент null — пароль здесь не нужен и не должен жить в контексте.

8. JWT + refresh token

Зачем нужна пара

AccessRefresh
НазначениеХодить к API.Получить новую пару без пароля.
Срок у нас15 минут.7 дней.
ВидПодписанный JWT.Случайный UUID.
Где проверяетсяПодпись + срок в JWT filter.Запись в PostgreSQL: hash, expiry, revoked.
Куда посылаетсяКаждый защищённый запрос.Только /login/refresh.

Аналогия завода

Access — сменный пропуск на турникет, действующий 15 минут. Refresh — талон в бюро пропусков на неделю. Турникет не принимает талон; бюро не требует паспорт, пока талон жив. В журнале бюро фиксируется, какой талон кому выдали и не сдан ли он. Logout — сдать талон; текущий пропуск максимум 15 минут ещё может быть действителен, но новый уже не выдадут.

Полный алгоритм

1. Login: пароль -> access JWT + raw refresh UUID 2. БД: SHA-256(raw refresh), user, expiresAt, revoked=false 3. API: только Bearer access 4. Access expired: POST /login/refresh { refreshToken: raw } 5. БД: hash -> find -> !revoked -> !expired 6. Rotation: old.revoked=true; create new refresh; create new access 7. Клиент заменяет обе строки 8. Logout: revoke refresh (или все refresh пользователя) + очистить клиент

Почему SHA-256 для refresh и BCrypt для пароля

У пароля известен пользователь: можно взять его hash из записи и спросить BCrypt matches(raw, hash). У сырого refresh сначала нужно найти, какая строка ему соответствует. BCrypt от одной строки каждый раз выдаёт другой результат из-за соли, поэтому findByTokenHash(passwordEncoder.encode(raw)) не найдёт запись. SHA-256 детерминирован: один raw всегда даёт один hex hash, который можно индексировать и искать.

Как дописать D: refresh endpoint

  1. Создать RefreshRequest(@NotBlank String refreshToken).
  2. Создать exception, который в advice отдаёт 401 одинаково для not found/revoked/expired.
  3. В сервисе пометить метод @Transactional.
  4. Посчитать SHA-256 raw, найти строку по findByTokenHash.
  5. Проверить revoked и expiresAt.
  6. Поставить старому revoked=true.
  7. Создать новый refresh через существующий createRefreshToken(username).
  8. Создать access через JWTService.generateToken(username).
  9. Вернуть LoginResponse.
  10. Проверить Postman: login → refresh → повтор старого refresh = 401.

Redis для refresh: «круче» ли?

Нет, не «круче», а другой storage. Redis хорош для очень быстрых короткоживущих записей и умеет TTL. PostgreSQL лучше подходит текущему учебному проекту: уже есть Liquibase, запись переживает рестарт Redis, видно историю и revoked. Сначала закрыть протокол на Postgres. Redis имеет смысл позже при реальной нагрузке или отдельной учебной цели.

9. OAuth 2.0

Что это и чем не является

OAuth 2.0 — протокол делегирования доступа. Он отвечает на вопрос: «может ли приложение получить ограниченный доступ к ресурсу пользователя, не узнавая его пароль?» Сам OAuth не равен JWT, не равен login и не гарантирует, что вы знаете имя человека.

Пример: сайт-планировщик просит доступ к Google Calendar. Пароль Google вводится только на стороне Google. Планировщик получает access token с scope «читать календарь», но не пароль.

Authorization Code + PKCE — современный поток для браузера

1. Client -> Authorization Server: /authorize?client_id&redirect_uri&scope&code_challenge 2. User логинится у провайдера и подтверждает consent 3. Authorization Server -> redirect_uri?code=ONE_TIME_CODE 4. Client -> /token: code + code_verifier 5. Authorization Server -> access token (+ ID token при OIDC, возможно refresh) 6. Client -> Resource Server: Bearer access token

PKCE защищает код авторизации от перехвата. Клиент заранее создаёт случайный code_verifier, в /authorize отправляет только его производный code_challenge, а на /token раскрывает verifier. Украденный code без verifier обменять нельзя.

10. OpenID Connect (OIDC)

Название «OpenID» в современном Java/Spring контексте почти всегда означает OpenID Connect (OIDC), слой идентификации поверх OAuth 2.0. OAuth говорит: «вот ограниченный доступ к API». OIDC добавляет: «вот проверяемое утверждение, кто пользователь».

ID token

OIDC выдаёт ID token, обычно JWT. Он адресован клиентскому приложению, а не ресурсному API. В нём встречаются claims iss (кто выдал), aud (для какого client_id), sub (стабильный ID пользователя), exp, nonce, иногда name/email.

Access token и ID token не взаимозаменяемы. API должен принимать access token, а frontend использует ID token/claims для сведений о вошедшем пользователе. Нельзя послать ID token в защищённый API «потому что это JWT».

Discovery и JWKS

Провайдер OIDC публикует /.well-known/openid-configuration: URL /authorize, /token, issuer, JWKS URI и поддерживаемые scopes. Через JWKS ресурсный сервер получает публичные ключи провайдера для проверки асимметричных подписей. Это отличается от нашего HMAC: у нас один секрет знают обе стороны; у OIDC private key остаётся у провайдера, а проверяющие получают public key.

11. Как реализовать OAuth 2.0 / OIDC в Spring

Сначала выбрать роль приложения

Наша рольSpring starterКогда
OAuth2 Clientspring-boot-starter-oauth2-client«Войти через Google/Keycloak».
Resource Serverspring-boot-starter-oauth2-resource-serverНаш API принимает access tokens внешнего issuer.
Authorization ServerSpring Authorization Server или KeycloakМы сами выдаём OAuth tokens многим клиентам. Отдельная большая задача.

Вариант 1: Login через Keycloak / Google (OAuth2 Client + OIDC)

  1. Зарегистрировать client у провайдера; получить client-id, redirect URI и (если confidential client) secret.
  2. Добавить oauth2-client starter.
  3. Добавить spring.security.oauth2.client.registration в yaml.
  4. Разрешить /oauth2/** и /login/**.
  5. Включить oauth2Login.
  6. После успеха сопоставить внешний issuer + sub с внутренним User и его permissions.
  7. Решить, как наш SPA получает сессию/собственный access; не смешивать случайно external ID token и API token.
dependencies {
    implementation("org.springframework.boot:spring-boot-starter-oauth2-client")
}

spring:
  security:
    oauth2:
      client:
        registration:
          keycloak:
            client-id: warehouse-web
            client-secret: ${KEYCLOAK_CLIENT_SECRET}
            scope: openid, profile
        provider:
          keycloak:
            issuer-uri: https://id.example.com/realms/warehouse

scope: openid переключает OAuth-клиента в OIDC-режим. issuer-uri позволяет Spring найти discovery-документ сам. Секреты не коммитятся в application.yaml.

Вариант 2: наш API — Resource Server

  1. Добавить resource-server starter.
  2. Настроить issuer-uri провайдера.
  3. Заменить самописный JWT filter на oauth2ResourceServer(o -> o.jwt()) после отдельного изучения migration.
  4. Настроить converter claims/scopes внешнего token в наши GrantedAuthority.
  5. Оставить бизнес-проверки на уровне метода/сервиса.
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://id.example.com/realms/warehouse

http.oauth2ResourceServer(oauth2 -> oauth2.jwt());

Что выбрать этому проекту сейчас

Ничего из OAuth/OIDC пока не внедрять поверх незавершённого refresh. У нас один SPA, один backend, свои пользователи и permissions. Самописный login+JWT — учебно оправдан. OAuth/OIDC стоит брать отдельной темой после security-конспекта: например, Keycloak как внешний IdP и сценарий SSO. Распиливать auth в микросервис или поднимать Authorization Server «для галочки» не нужно.

12. Шпаргалки

Что сказать себе утром перед работой

Формула: Login проверяет пароль и выдаёт билет. Обычный запрос проверяет билет и наполняет SecurityContext. Авторизация смотрит authorities. Refresh не ходит к API: он меняет старый длинный талон на новую пару билетов.

Чеклист: добавить защищённую сущность

  1. Добавить коды permissions в enum и данные миграцией.
  2. Убедиться, что AppPrincipal.getAuthorities() получает эти permissions через роли.
  3. Поставить @PreAuthorize на read/write методы.
  4. Проверить 401 без access, 403/доступ с разными authorities.
  5. Доработать фронтенд-права по правилу проекта; UI — удобство, сервер — реальная защита.

Чеклист: закончить refresh

  1. DTO RefreshRequest.
  2. Единая 401 ошибка для invalid/revoked/expired refresh.
  3. Transactional validate + revoke old + create new.
  4. POST /login/refresh.
  5. Postman rotation test.
  6. Frontend: accessToken и refreshToken; один retry на 401.
  7. Logout revoke + очистка storage.
  8. Тесты auth/refresh.

Никогда не делать

  • Не класть сырой пароль, JWT secret, client secret или сырой refresh в Git, логи и exception message.
  • Не считать Base64 шифрованием.
  • Не доверять скрытой кнопке как проверке права.
  • Не использовать ID token вместо access token в API.
  • Не отключать CSRF «на всякий случай» при переходе на cookie/session auth.
  • Не превращать OAuth в задачу «сделать JWT посложнее»: это разные уровни.

Конец конспекта. Актуализируй разделы 8 и 12 после завершения refresh/logout и перед внедрением OAuth/OIDC.
